# ADR-0011: A Tier can set a minimum for an integer Privilege

- **Status:** accepted; not implemented. It is built on the Python service only, after the console switches to it (OPE-45). No protocol change.
- **Date:** 2026-11-13
- **Builds on:** [ADR-0008](ADR-0008.md) (Tiers and Organization terms per Product), [ADR-0009](ADR-0009.md) (the Python service), [ADR-0010](ADR-0010.md) (its clarifications).

A business sells a Tier with a floor, for example "Enterprise starts at 50 seats". Today a Manager can save Enterprise Organization terms of `seat_max: 10`, and nothing in the Tier says that is below what Enterprise is sold as. The Catalog's own minimum and maximum apply to every Tier alike, so they cannot express it.

**Decision.** A Tier can set a **Tier minimum**: the lowest value an integer Privilege may have on that Tier, for example "Enterprise: `seat_max` ≥ 50".

- **Scope.** Only integer Privileges. A Tier has at most one minimum per Privilege. There are no Tier maximums for now. The Catalog's own minimum and maximum still apply.
- **What it applies to.** The Tier's standard variant and Organization terms on that Tier cannot go below it. Trial and grace variants do not have to meet it.
- **When it is checked.** When Organization terms are saved, when an Organization is given the Tier, and when the minimum itself changes.
- **Never changed silently.** Raising a minimum above existing Organization terms is refused, and the refusal lists those Organizations. No stored value is changed to meet a minimum.
- **Minimum commitment.** A commitment such as "commits to 10M tokens a week" is a **Minimum commitment**. It is recorded on the Organization's contract and only displayed. Charging for it stays out of scope.
- **Where it is built.** On the Python service only, after OPE-45 switches the console to it and retires the Node service.

**A Tier minimum constrains authoring, not evaluation.** It is checked when values are saved, never when they are resolved. Spec [Requirement 1.5.2](spec/sections/01-data-model.md#requirement-152) still lets an override be lower than the plan value, and resolution ([§3](spec/sections/03-resolution.md)) does not read Tier minimums, so OEREP and the SDKs do not change.

## Considered options

- **Call it a "requirement".** Rejected because it collides with required Privileges (an editable Privilege without a default must be supplied in every Tier variant) and with OEREP's `requiredPlan`.
- **Call it a "condition".** Rejected because it collides with environment prerequisites.
- **Enforce it during evaluation.** Rejected because Requirement 1.5.2 lets an override be lower than the plan value, and the protocol would have to change.
- **Raise existing Organization terms to a new minimum automatically.** Rejected because negotiated terms would change without anyone deciding it.
- **Tier maximums too.** Not now.

## Consequences

- The protocol, the SDKs and resolution are unchanged.
- Only the standard variant and Organization terms are checked against a Tier minimum; trial and grace variants are not.
- Allowances that reset per period ("10M tokens a week") are a separate proposal, [RFC-0006](docs/rfcs/0006-periodic-allowances.md). A Minimum commitment is recorded and displayed, not enforced or charged.
