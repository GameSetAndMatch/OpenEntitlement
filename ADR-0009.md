# ADR-0009: The service is a three-layer Python application

- **Status:** accepted; in progress on the `service/python` branch (foundation: OPE-37; sign-in, Workspaces, Products and per-Product roles: OPE-38). Amends [RFC-0004](docs/rfcs/0004-mcp-server.md): the MCP server is built with FastMCP inside the Python service, not in the Node service.
- **Date:** 2026-11-13

The reference service (Workspace API, sign-in, OEREP evaluation) is TypeScript on Node today, while the Python SDK already carries the canonical Pydantic models ([ADR-0006](ADR-0006.md)). The service now needs an MCP server ([RFC-0004](docs/rfcs/0004-mcp-server.md)), Products ([ADR-0008](ADR-0008.md)) and per-Product authorization. Building them once, in the language that owns the models, is cheaper than building them in Node and keeping two implementations of the same rules.

**Decision.** The service is rewritten in Python, managed with uv, on FastAPI. It has three layers:

1. **Interfaces.** The HTTP API (FastAPI) and the MCP server (FastMCP 2.x) are two front doors. Authentication and authorization run as middleware and dependencies before any handler. Neither interface contains business rules or database access: both call the service layer.
2. **Service layer.** One implementation of every operation (define a Privilege, assign a Tier, resolve a value, preview and apply a change) and its rules, Permissions and audit. It defines the repository contracts it needs as Python protocols, for example `PrivilegesRepository`.
3. **Repositories.** Implementations of those contracts for a database, for example `PostgresPrivilegesRepository` implements `PrivilegesRepository`. Only this layer knows SQL. Each table is defined once as a SQLAlchemy Core `Table` in this layer, without the ORM. Repositories query through SQLAlchemy Core's async engine with the asyncpg driver, and Alembic generates and applies migrations from the same table definitions. The service layer never sees SQLAlchemy: it works with its protocols and the SDK's Pydantic models.

**Errors.** Every error, on the HTTP API, OEREP and MCP alike, is a typed exception defined once, with a stable problem type, an HTTP status and its parameters. The service layer raises these exceptions and never builds responses. A single exception handler turns any of them into an [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details response (`application/problem+json`, with `type`, `title`, `status`, `detail`, `instance` and the parameters as extension members). An unexpected exception becomes a generic 500 problem that never exposes internals. No handler or route writes an error body of its own. The problem `type` is the stable identifier (for example `https://openentitlement.dev/problems/revision-conflict`) and has a short page on the website; `title` and `detail` are in the signed-in Account's language when there is one, and otherwise in the service's documented default language (for example for API-key callers and failed sign-ins); `type` and the extension members are language-independent. A rejected request is one `validation-failed` type whose `errors` list names each field as a JSON Pointer with its message. An MCP tool error carries the same problem object in its structured content. OEREP adopts Problem Details in place of `{error, message}`, as part of the 0.1 amendment in [RFC-0005](docs/rfcs/0005-product-scoped-evaluation.md).

**Data.** Each kind of record has its own table (Products, Privileges, Groups, Tags, Tiers, Tier variants, Organizations, Personal terms, grants, members, API keys, audit entries), and each record carries its own version for optimistic concurrency, instead of one revision per Workspace. Postgres row-level security stays as a second safety net: every request runs in a transaction bound to its Workspace. Behind a transaction-mode connection pooler, asyncpg's prepared-statement cache is turned off.

**Resolution.** The service layer resolves values with the Python SDK's resolution engine, which passes the shared conformance suite, so the service and the SDK cannot disagree.

**Sign-in.** Console sessions use OIDC with a session cookie. Applications calling OEREP use API keys bound to one Product ([ADR-0008](ADR-0008.md)). MCP clients use OAuth 2.1 with the service as authorization server ([RFC-0004](docs/rfcs/0004-mcp-server.md)), built on Authlib. Authentication and per-Product authorization run as middleware and dependencies.

**Delivery.** The Python service is built with Products, per-Product roles and the Product-scoped OEREP paths from its first version, on its own branch, and replaces the Node service in one switch once the existing browser tests pass against it. No Workspace exists yet, so nothing runs side by side or is migrated. Internationalization, the account menu and the MCP server are built on the Python service, not on Node first.

Dependencies point inward: interfaces depend on the service layer, repositories implement the service layer's protocols, and the service layer depends on neither. Tests can run the service layer against in-memory repositories.

## Implementation notes

These clarify how the decision is carried out; they do not change it.

- **Product Catalog (OPE-39).** Groups, Tags and Privileges have separate Product-scoped tables, canonical SDK Pydantic payloads and per-record versions. Catalog writes lock the Product while checking references and variant values, then atomically save the record, supplied versioned variant values and authenticated audit facts. The lock prevents hierarchy/reference races; it does not create a Product-wide edit version. OPE-40 must use this same lock and the Catalog-facing variant value repository when introducing Tier lifecycle operations; OPE-43 supplies the filtered audit read side.
- **Tiers (OPE-40).** Tiers and the status policy have Product-scoped tables with their own versions; Tier variants stay rows of the Catalog's variant table, now with their Tier and purpose. Every Tier write first takes the Catalog's Product row lock and reads the Catalog in the same transaction, so a Privilege without a default and a new Tier variant cannot both commit without the variant's value. Tier writes record authenticated audit facts (`tier_changes`).
- **Organizations (OPE-41).** Organizations have a Workspace table; each Organization's Tier variant in a Product (with its status, grace end and Organization terms) is a row of its own with its own version, referencing the variant so a used Tier cannot be deleted. These writes take the same Product row lock as the Catalog and Tiers. Values are resolved by the SDK's `resolve_from_facts`: each Tier variant is a plan, Organization terms are Organization-scoped overrides of the variant in effect, and a Read-only Privilege has neither. The contract status first picks the variant in effect (the grace variant during past-due grace, then the status policy).

- **Row-level security needs a role that cannot bypass it.** Postgres skips row-level security for superusers and roles with `BYPASSRLS`. Each request transaction therefore switches to the `openentitlement_service` role (created by the first migration, `NOBYPASSRLS`) and binds the Workspace in the `openentitlement.workspace_id` setting; every Workspace table forces a policy on that setting. The service's connecting role must itself be neither superuser nor `BYPASSRLS`, or code running in a transaction could leave the role with `RESET ROLE`.
- **Validation errors outside the body.** `validation-failed` names a body field with a JSON Pointer into the body (`/tiers/1/name`), a query, path or header parameter with its location first (`/query/limit`), and unparseable JSON with the empty pointer `""`.
- **Listing an Account's Workspaces.** The Workspace switcher reads across Workspaces. A transaction may therefore also bind an Account (`openentitlement.account_id`), and read-only policies let it see that Account's own memberships and Product roles, the Workspaces they belong to, and every Workspace when the Account is a Platform administrator. Writes remain bound to the transaction's Workspace. Accounts, sessions and sign-in flows belong to no Workspace and have no row-level security.
- **Console sign-in.** The OIDC client runs in the HTTP interface with Authlib's ID-token claim rules, joserfc signature checks and httpx; it accepts only asymmetric signing algorithms. Sign-in flows and sessions are stored as SHA-256 hashes, sessions last 12 hours, and a state-changing request needs the console's `Origin` and the session's CSRF token. The service layer decides who may sign in (verified email, allowed domains, the bootstrap Platform administrator). Configuration keeps the Node service's variable names (`OE_APP_URL`, `OE_OIDC_*`, `OE_PLATFORM_ADMIN_SUBJECT`, `OE_SIGNUP_DOMAINS`).
- **Authorization refusals.** A Workspace the Account is not a member of, and a Product where it has no Role, are `not-found`, so their existence is not revealed; a visible record the Role cannot change is `permission-denied`. Further problem types: `sign-in-required`, `sign-in-failed`, `sign-in-refused`, `csrf-rejected`, `revision-conflict`, `already-exists`, `product-in-use` and `last-product`.
- **Problem types of the foundation.** `validation-failed` (400), `not-found` (404), `method-not-allowed` (405), `internal-error` (500) and `service-unavailable` (503, from the health check), each with a page under [openentitlement.dev/problems](https://openentitlement.dev/problems/). An HTTP error raised by the framework itself that no type describes (for example 413) is RFC 9457's untyped `about:blank` problem rather than a 500.

## Considered options

- **Keep the Node service and add a Python MCP process beside it.** Rejected because every rule would exist twice, once for the console API and once for MCP, and the two could disagree.
- **Keep everything in Node with the TypeScript `fastmcp` library**, as RFC-0004 assumed. Rejected because the canonical models and their validation live in the Python SDK.
- **Plain psycopg SQL with hand-written migrations.** Rejected because the schema would be described twice and Alembic could not detect drift.
- **An ORM model shared by all layers.** Rejected because it couples business rules to table shapes. The repository protocols keep the service layer independent of the database.

## Consequences

- The Node service in `console/server` is retired once the Python service reaches parity. The console web application (React) stays TypeScript; it is a client of the HTTP API.
- The Docker image and Helm chart ship a Python runtime instead of Node for the service.
- The existing browser tests become black-box parity tests for the new service.
