# ADR-0007: The Audit log is for Managers and Owners and names what changed

- **Status:** accepted; implemented preview on `service/python` (OPE-43)
- **Date:** 2026-11-12

Every Workspace member, including a User, can read the Audit log today. Each entry shows the actor's Account ID and a generic action such as `tiers:write`. Those IDs are unreadable, and showing emails instead would let Users see emails they cannot see in Members.

**Decision.** Only Managers and Owners (and Platform administrators) can read the Audit log. Under [ADR-0008](ADR-0008.md), each entry records its Product scope when it is written. A Product's Manager receives only entries about the Products they manage, and only the fields and before → after values for those Products. An entry about a shared record, such as an Organization or a member with roles in several Products, never shows another Product's values or roles. Workspace-wide entries, such as Products, Owners and the Cloud service tier, are for Owners and Platform administrators only. A regression test covers one Account with roles in two Products. The service enforces this, not only the console. Entries show the actor's email.

Each entry records what it changed when the change is made: the kind of record, its ID and its name at that moment (for example "Organization Acme"). The log never reconstructs that later from the current Workspace, so an entry still reads correctly after a rename or deletion.

An entry reads as one sentence, such as "alice@acme.com changed Organization Acme's terms". It can be expanded to list only the values that changed, as before → after (Seats 10 → 20).

## Considered options

- **Everyone can read it, without emails.** Rejected because an actor's name alone is ambiguous, and the log answers "who changed this", which Users do not need to administer anything.
- **Derive the target from the stored before/after data when the log is displayed.** Rejected because it depends on the current shape of the Workspace data, and it breaks for deleted records.

## Consequences

- A User loses access to the Audit log. This is a behavior change for the Workspace preview.

## Python service implementation (OPE-43)

All service writes share `audit_entries`, with the authenticated actor and target snapshot recorded in the write transaction. Product IDs are captured on the entry or its changed fields. Owners and Platform administrators read the Workspace log; Managers receive only managed Products' fields. A reason is withheld whenever some changed fields are hidden. Users receive `permission-denied` (403), the service's typed authorization problem. Workspace row-level security applies to audit entries too.

`GET /api/workspaces/{workspace_id}/audit` returns `{entries, next}`, newest sequence first. `limit` is 1–200 (default 50); `before` is the positive exclusive sequence returned as `next`. Visibility is applied before page size. Sequences are continuation tokens, not record versions; audit snapshots are immutable. No additional search filters are defined by OPE-43. The console offers continuation and expandable changes; fixed entry text supports English and French. Account-language persistence is delivered separately by the internationalization ticket.

An Organization's Tier variant is compared by its ID and recorded with its name at that moment (`beforeName`/`afterName`): names need not be unique, so the name is shown but never decides whether something changed. API key creation and revocation (OPE-42) record Product-scoped `API key` entries with the key's ID and name, never its secret or hash.

Migration `0008_audit_log` replaces the earlier write-fact tables; as the project specifies, there are no existing Python Workspaces to migrate. `0009_merge_audit_api_keys` joins it with OPE-42's `0008_api_keys` into one head; a database at either 0008 revision upgrades to it. This remains integration-branch preview behavior, not a released protocol change.
