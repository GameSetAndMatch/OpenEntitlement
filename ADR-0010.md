# ADR-0010: Python service decision clarifications

- **Status:** accepted direction; implementation varies by ticket. This record makes no released protocol change.
- **Date:** 2026-11-13
- **Amends:** [ADR-0008](ADR-0008.md), [ADR-0009](ADR-0009.md), [RFC-0005](docs/rfcs/0005-product-scoped-evaluation.md).

The user approved all fourteen pending decisions. These settle questions without marking implementation tickets complete. `service/python` is an integration preview, not a release.

| Question | Accepted decision | Delivery scope |
|---|---|---|
| Q1 | Status policy belongs to each Product, with separate `past_due` and `ended` actions: read-only or a fallback variant in that Product. | OPE-40, OPE-42 |
| Q2 | Status and grace belong to each Organization/Product assignment. Past due uses the Tier's grace variant until its snapshotted deadline, then the Product policy. Repeated past due on the same Tier preserves the deadline; changing Tier starts its grace window. Reactivation ends the episode; ended bypasses grace. | OPE-41, OPE-42 |
| Q3 | An archived Tier cannot be a newly chosen fallback. An unchanged persisted fallback may remain after its Tier is archived and continues serving existing assignments. | OPE-40 |
| Q4 | Request validation returns HTTP 400 with the stable `validation-failed` Problem Details type and field errors, rather than FastAPI's default 422 shape. | OPE-37, OPE-42 |
| Q5 | Require a database unless in-memory operation is explicitly selected with `OE_IN_MEMORY=true`. Missing database configuration never silently selects volatile storage. | OPE-37 |
| Q6 | Archived Products count toward Cloud Pro's one-Product limit. Self-hosted Product counts remain unrestricted. | OPE-44 |
| Q7 | A refused Enterprise-to-Pro downgrade lists every Product, including archived Products. The customer chooses which to retain; the service does not choose or delete for them. Archiving does not reduce the count. | OPE-44 |
| Q8 | Promotion to Workspace Owner removes Product roles. Owner authority covers every Product. | OPE-44 |
| Q9 | A non-Owner with no remaining Product role leaves the Workspace; there is no role-less membership. | OPE-44 |
| Q10 | A Manager of any Product may create or rename a shared Organization. Assignment changes require Manager authority in that Product, or Workspace Owner authority. | OPE-41 |
| Q11 | Boolean environment prerequisites only restrict (entitlement AND environment). Only Platform administrators may change their bindings; integer/string bindings remain out of scope. | OPE-39, OPE-42 |
| Q12 | Grants are uncapped additive allowances: resolution may exceed the authored maximum. Existing type, scope and read-only validation still applies. | OPE-60, OPE-42 |
| Q13 | Move delete-application-user reason from URL query to a typed request body in a small follow-up, preserving audit, reason validation, version checks and authorization. | Follow-up pending |
| Q14 | OPE-52 research uses 3–5 unfamiliar developers. Participants are unnamed and no contacting is authorized. Human research remains pending. | OPE-52; owner action |

For example, Analytics can be past due while Storage stays active for the same Organization. Analytics' Manager can rename that Organization but cannot assign its Storage Tier. An integer allowance of 100 plus a Grant of 20 resolves to 120 even with authored maximum 100.

## Source evidence and delivery limits

Inspected on the `service/python` base, under `sdk-python/packages/service/src/openentitlement_service/`:

- `services/tiers.py` stores Product policies and rejects newly selected archived fallbacks while allowing unchanged ones.
- `services/organizations.py` stores assignment status/deadlines, scopes assignment permission to the Product, and validates positive integer Grants without an authored maximum cap; its SDK adapter supplies resolution facts.
- `services/members.py` removes Product roles on Owner promotion and membership after the last Product role is removed. `services/workspaces.py` counts all Products and lists their names on a refused downgrade.
- `services/catalog.py` limits environment binding changes to Platform administrators. `services/problems.py` defines validation status 400. `main.py` requires a database unless in-memory operation is explicit.

These are source observations, not runtime verification or evidence of completed OPE-42 transport/conformance work. Released SDKs and the normative specification retain their existing contracts until RFC-0005's coordinated handoff. No compatibility wire fields change here.

## Q13 follow-up and tracker handoff

The current DELETE application-user route in `sdk-python/packages/service/src/openentitlement_service/interfaces/http/organizations.py` accepts `version` and `reason` in the query. Move `reason` into a typed body, update the console caller, and cover missing/blank reasons, successful authenticated audit, stale versions and cross-Product denial with relevant HTTP/browser regressions. Keep this separate from OPE-42.

Linear was not connected in this session: no issue/project comments were updated and no Q13 ticket was created or confirmed absent. Before creating one, search existing issues for this route/reason change, reuse a match or create a focused follow-up linked to OPE-60. Q14 is not satisfied by documentation or automated tests; OPE-52 awaits human research evidence.
