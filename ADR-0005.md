# ADR-0005: Portable user entitlements and hosted capability packaging

- **Status:** accepted direction; implementation in the Workspace preview. "A Workspace owns one Privilege Catalog" is superseded by [ADR-0008](ADR-0008.md): each Product has its own Catalog.
- **Date:** 2026-11-09

An application user is an Organization-scoped **Subject**, not an OpenEntitlement console Account or membership Role. A Workspace owns one Privilege Catalog. Users inherit resolved Organization values; explicit personal terms replace values, and positive integer grants add allowances. Personal terms bind to the assigned Tier variant and become inactive after a variant change; grants retain their user scope across changes, matching v1's grant model. Grace/fallback suspend those exceptions. Read-only status, frozen defaults and restrictive boolean environment prerequisites remain final constraints. Evaluation does not consume usage or replace application authorization.

OpenEntitlement Cloud Pro supports Organization scope. Cloud Enterprise adds user scope as a platform-owned capability. This is distinct from the Tiers a business authors for its own Organizations. Workspace Owners cannot upgrade Cloud capabilities by editing their Catalog; a Platform administrator assigns them with audit and revision control. Downgrades retain records and explicitly reject unsupported user evaluation rather than silently broadening it to the Organization. Self-hosted installations retain user scope. Billing automation and enterprise compliance are not implied.

The open protocol/SDKs keep their existing subject model available to every implementation. Commercial packaging never changes the portable wire contract. The Workspace preview remains a separate transport until a conformance-tested OEREP bridge exists; do not silently claim it works through the current RemoteProvider.

Use flat authoring keys such as `seat_max` and separate Group/Tag metadata. Dotted keys are no longer accepted anywhere (2026-11-10): no one used them yet, and they are not valid identifiers in Python. Keys match `^[a-z][a-z0-9_]*$`. Example Catalog updates are not a data migration.

Strict Pydantic authoring is optional in Python (`openentitlement-sdk[authoring]`); Zod is an optional TypeScript authoring subpath. Browser and server share the TypeScript model. Python authoring reuses the standard-library domain invariants, with parity tests for serialized values. Runtime evaluation imports stay dependency-free. This extends ADR-0003's dataclass approach without requiring validation libraries for all SDK consumers. *(Superseded by [ADR-0006](ADR-0006.md): Pydantic is a core Python dependency, the `[authoring]` extra is removed, every Python model is a Pydantic model, and Zod becomes a required TypeScript core dependency.)*

**Implementation note (2026-11-12, OPE-55):** the console names where each resolved value comes from in glossary terms (Catalog default, the Tier variant's name, Organization terms, Personal terms, Grace period) instead of raw codes. A Grant shows the one-line sum it adds to, for example "Personal terms 50 + Grant 5". The workspace model returns this layer as `source` beside the unchanged `reason`.

**Trade-off:** authoring dependencies improve validation and introspection while preserving a small runtime. Two language implementations still need contract/parity tests. Workspace JSON storage and whole-state audit are a bounded development preview, not a scaling claim for large user directories.
