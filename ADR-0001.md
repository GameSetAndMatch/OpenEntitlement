# ADR-0001: A specification plus providers, not another entitlements service

- **Status:** accepted (v0.1.0 draft)
- **Date:** 2026-11-03
- **Deciders:** OpenEntitlement maintainers

## Context

Every production-grade entitlements system today is a **service** tied to its vendor's data model: Stripe Entitlements, Stigg, Schematic, and Planship on the SaaS side, and Lago, OpenMeter, Flexprice, and Autumn on the open-source side ([PRIOR_ART.md](PRIOR_ART.md)). Each one has its own SDK, its own idea of a plan, and its own denial shape. Three problems follow:

1. **Lock-in at the call site.** Gates (`if (await stigg.getMeteredEntitlement(...).hasAccess)`) are spread through the application. Switching vendors means rewriting every one of them, plus their tests.
2. **Self-hosted and contract customers don't fit.** Without a subscription in the vendor's billing system, most models can't say what a customer may do. A self-hosted install can't call a SaaS at all.
3. **Billing leaks into product logic.** Denial reasons like `NoActiveSubscription`, overrides keyed to subscription ids, and feature changes that wait for the next billing period all come from the billing system and end up in application code ([vendor mapping](PRIOR_ART.md#vendor-mapping)).

Feature flags had the same problem, and **OpenFeature** solved it without building another flag service. It defined one evaluation API, a provider interface, hooks, an evaluation context, and a Gherkin conformance suite. Vendors (LaunchDarkly, Flagsmith, Flipt, …) then implemented providers. Flipt went further and implemented OFREP, so one server-side endpoint reaches every OFREP-capable SDK.

## Decision

OpenEntitlement is a **specification** (`spec/`), a **conformance suite** (`spec/assets/gherkin`), and **reference SDKs** whose core contains no vendor code. Concretely:

1. **The spec is the product.** Numbered RFC 2119 requirements, each one testable through a tagged Gherkin scenario. An implementation is conformant when it passes the suite for the capabilities it declares.
2. **The application talks to an API, and a provider supplies the answers.** `isEnabled`, `getLimit`, `requireWithin` (plus `guard`, `getEnum`, `getDetails`, `requiredPlan`) are the whole application surface. Providers implement `resolve`, and optionally mutations and `suggestPlan`.
3. **Resolution semantics live in the spec, not in providers.** The SDKs ship the algorithm as a pure function (`resolveFromFacts`). A facts-based provider only reads facts (assignment, plan values, overrides, grants), so it can't drift. Resolving providers (vendor adapters) are held to the same semantics by the conformance suite.
4. **Core packages have zero dependencies.** `openentitlement` (Python) and `@openentitlement/core` (TypeScript) depend on nothing. Postgres (`psycopg` / `pg`) and Stripe (no SDK, just HTTPS calls) ship as separate packages.
5. **Concurrency is a lock, not a provider feature.** Serializing check-then-act depends on where *usage* lives (usually the application's database), not on where *limits* come from. So `guard` takes a pluggable lock (in-process, Postgres advisory, …) that composes with any provider.
6. **Audit goes through hooks plus provider durability.** Mutation hooks (`before`/`after`/`error`/`finally`) receive `{actor, reason, before, after, at}` for forwarding and veto. Providers persist the same event atomically with the change.
7. **The scope is the entitlement layer only.** No authentication, no RBAC, no feature flags. The spec interoperates with OpenFeature and never replaces it.

## Alternatives considered

### A. Build another entitlements service (open source)

One server with a REST API, dashboards, and SDKs, like Lago or OpenMeter.

- ➕ One thing to run. Easy to demo.
- ➖ It is *a fifth vendor*. It doesn't remove lock-in, it moves it. Existing open-source systems would have to be migrated off instead of adopting a standard.
- ➖ It forces a deployment on self-hosted installs that need none (the `FixedProvider` case).
- ➖ It competes with Lago, OpenMeter, and Flexprice instead of giving them a common surface.

**Rejected.** A reference service MAY appear later as *one* OEREP implementation, but it will never be required.

### B. Extend OpenFeature (model entitlements as flags)

Use `getNumberValue("seats.max")` with an entitlement-backed provider.

- ➕ No new SDK. OpenFeature is already a CNCF incubating project.
- ➖ It merges two layers: rolling back a release would revoke a paid entitlement, and granting an entitlement would release code. Some vendors already ship this merge, and it is exactly what [§9](spec/sections/09-interoperability.md) forbids.
- ➖ Flag semantics have no plan values, overrides bound to plans, additive grants, `UNLIMITED`, usage checks, shared pools, `requiredPlan`, or audited mutations. Encoding them in flag metadata would fragment by vendor again.
- ➖ The evaluation context keys on a *user* (`targetingKey`). Entitlements key on an *organization*.

**Rejected,** but the hook model, the provider model, the resolution details, and the conformance approach are copied deliberately, so teams that know OpenFeature feel at home and one telemetry hook can serve both.

### C. Use an authorization engine (OpenFGA, Oso, Cerbos)

Model plans as relations: `organization:acme#plan@plan:pro`, `plan:pro#feature@feature:sso`.

- ➕ Mature engines that are good at "can X do Y".
- ➖ Quotas, usage, grants, and `UNLIMITED` don't fit relationship tuples. "How much?" is the question that matters.
- ➖ It folds the commercial layer into RBAC. Entitlement and RBAC failures need different UX (an upsell versus "ask your admin").

**Rejected as the model.** An authz engine can still be a provider backend.

### D. A library only, with no spec

One good embedded library (like Limitr).

- ➕ Fast to ship.
- ➖ There is no way for Stripe, Stigg, or Lago adapters to prove they behave the same. Another language means a re-implementation that drifts.

**Rejected.** The SDKs are reference implementations of the spec, and they pass the same Gherkin files.

## Consequences

**Positive**

- Applications write gates once. Switching vendors means swapping the provider, and the conformance suite says whether the new one behaves the same.
- Self-hosted installs use `FixedProvider` with no network call and no special-case code.
- Billing systems (open source or SaaS) can adopt the standard cheaply: a facts adapter of about 100 lines reusing `resolveFromFacts`, or, from v0.2, one OEREP endpoint.
- The Postgres schema is shared across languages: a Python back office and a TypeScript API read the same `oe_*` tables (verified in development).

**Negative / risks**

- **Adoption risk.** A spec with no adopters is a document. Mitigations: reference providers that are useful on their own (in-memory, Postgres, fixed), a Stripe adapter proving the interface, and OEREP to lower the cost for servers.
- **Lowest common denominator.** Vendor-specific features (preflight/reservations, credit currencies, add-on catalogs) aren't in v0.1. Adapters may expose them outside the API. The spec grows by evidence.
- **Semantics have to be defended.** "Override replaces" and "grants survive plan changes" differ from some vendors' choices. Adapters for those vendors must translate, and some can't fully (Stripe declares no overrides or grants).
- **Two SDKs to keep in lockstep.** The shared Gherkin suite and the shared schema are the guardrails. Both runners execute the same files in CI.

## Changes to the starting model

The brief asked us to challenge the starting model, not copy it. These are the deviations, each with its reason in the spec:

| Starting model | Spec v0.1 | Why |
|---|---|---|
| `valueType ∈ {boolean, integer, string/enum}` | `enum` with **ordered** options, no free `string` | A free string can't be compared, so `requiredPlan` couldn't be computed ([Req 1.1.4](spec/sections/01-data-model.md#requirement-114)) |
| `isEnabled(feature)` | The feature names a **gate** privilege (implicit when it has only one) | A multi-privilege feature is otherwise ambiguous ([Req 1.1.6](spec/sections/01-data-model.md#requirement-116)) |
| Overrides bound "to the plan they were set on" | Bound to the plan **family** (`variantOf ?? id`) | So that converting `pro_trial` → `pro` doesn't make every negotiated override stale ([Req 1.3.3](spec/sections/01-data-model.md#requirement-133)) |
| Concurrency "defined, or a provider capability" | Neither: a **lock** strategy on the client, composable with any provider | Usage lives in the application's database, not the provider's ([§5](spec/sections/05-concurrency.md)) |
| Shared pools as subject grants | Plus a normative **draw order** (own allowance first), a `{pool, subject}` usage breakdown, and a `poolUsage` helper | So that the check is computable from resolution details alone, for every provider ([Req 3.3.3](spec/sections/03-resolution.md#requirement-333)) |
| Error carries `requiredPlan?` | Plus a defined candidate rule (public, base plans, higher rank, lowest first) and an RFC 9457 403 body with `error: "entitlement_required"` | So that two providers suggest the same plan, and UIs can tell an entitlement 403 from an RBAC 403 ([§3.4](spec/sections/03-resolution.md#34-required-plan), [§8.2](spec/sections/08-errors.md#82-http-mapping)) |
| Three calls | Three calls plus `requireEnabled`, `getEnum`, `getDetails`, `guard`, `requiredPlan` | Enum privileges and admin tooling need typed access, and check-then-act needs `guard` |
| `reason` `ERROR` | Errors **fail closed** to the privilege default, with no upsell | An outage mustn't grant paid features, or show an upgrade prompt to a customer who may already be entitled ([Req 3.1.11](spec/sections/03-resolution.md#requirement-3111)) |
