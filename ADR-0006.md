# ADR-0006: Core SDK dependencies, Pydantic models and camelCase JSON

- **Status:** accepted; supersedes the dependency-free core sentence of ADR-0001, the "dataclasses without a schema framework" sentence of ADR-0003 and the optional-authoring paragraph of ADR-0005
- **Date:** 2026-11-09

## Decision

**Core dependency rule.** A core SDK package depends only on the language runtime plus widely adopted, high-value libraries that most production SaaS applications already have: Pydantic 2 in Python and Zod in TypeScript. Anything else, including database drivers, stays an optional extra or peer dependency (`openentitlement-sdk[postgres]` adds only psycopg). Transports keep using the standard library (`urllib`, `fetch`). A new core dependency needs a superseding ADR.

**Models.** Every Python SDK model is a Pydantic `BaseModel`. That covers evaluation context, resolution details, facts, provider and mutation types, hook contexts and the Privilege Catalog. They share one base configuration: frozen and hashable, unknown fields rejected, camelCase aliases, and validation by name or alias. The TypeScript SDK adopts Zod schemas for the same models. That work is a separate change and does not alter the wire contract.

**Casing.** JSON, JSON Schema, OpenAPI and FastAPI responses use camelCase (`groupId`, `parentId`, `envOverride`, `organizationId`, `staleOverrides`). This applies to the Privilege Catalog as well as OEREP v1. Code uses the language's own convention: snake_case attributes and keyword arguments in Python, camelCase in TypeScript. Validation accepts both spellings in Python, so `Group(parent_id=...)` and `{"parentId": ...}` produce the same model. Python evaluation contexts given as dicts prefer `organization_id`; `organizationId` still works.

**Wire compatibility.** OEREP v1 JSON keeps its released meaning. Models with a wire form (`ResolutionDetails`, `GrantApplied`, facts, `AuditEvent`) serialize through their existing `to_dict`, so `model_dump_json()` and FastAPI responses match it. Absent optional members are omitted, UNLIMITED is `{"unlimited": true}` and timestamps use `isoformat()`. Evaluation contexts are not validated when constructed: an invalid tenant still resolves to `INVALID_CONTEXT` rather than raising (spec §2). The client builds already-validated internal copies without re-validating them on the evaluation hot path.

**Python version.** The minimum supported Python is 3.11, the oldest version we support for production customers. CI tests the minimum.

## Supersedes

- ADR-0001: "Core SDKs remain dependency-free." Transports remain standard-library only. The core may now require Pydantic or Zod under the rule above.
- ADR-0003: "The authoring contract is validated in TypeScript and Python dataclasses without requiring a new schema framework." The contract is now validated by Pydantic models in Python, with Zod planned for TypeScript.
- ADR-0005: "Strict Pydantic authoring is optional in Python (`openentitlement-sdk[authoring]`) … Runtime evaluation imports stay dependency-free." The `[authoring]` extra is removed. `pip install openentitlement-sdk` includes Pydantic.

## Consequences

Breaking for preview users of the Python SDK:

- Python 3.10 is no longer supported.
- Pydantic 2.12 or later is installed with the core.
- Privilege Catalog JSON keys are camelCase.
- Assigning to a frozen model raises Pydantic's `ValidationError` instead of `dataclasses.FrozenInstanceError`.
- `dataclasses.replace`/`asdict` no longer apply; use `model_copy`/`model_dump`.

Positional construction still works at runtime for compatibility. Type checkers treat the models as keyword-only, so new code should pass keywords.

Applications gain validated JSON input, JSON Schema and first-class FastAPI support with no adapter code. Construction cost rises: the reference hot path measured about 1.2–2.2 µs more per evaluation (see the PR benchmark), which is small next to any network or database provider. Two language implementations still need shared conformance and parity tests for serialized values.

## Validation and serialization details

Catalog optional members are omitted by ordinary Pydantic serialization, including
nested models and FastAPI responses. Explicit null Catalog members are rejected;
Python field names and camelCase aliases remain accepted. Unlimited requires the
complete object `{"unlimited": true}` with an actual boolean and no extra members.
Runtime `Limit` and `Value` unions use strict primitive types to preserve value kinds.
OEREP `planValue` presence survives Pydantic roundtrips, including zero, false, null
and Unlimited, without serializing the internal presence flag.
